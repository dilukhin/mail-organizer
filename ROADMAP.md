# Roadmap

## Общий принцип переходов

Новая возможность не получает write-права только потому, что реализована в коде. Переход выполняется через измеримый gate:

```text
read-only → dry-run → ограниченная обратимая запись → проверка → расширение scope
```

Если фактическое состояние после действия отличается от ожидаемого, дальнейшее расширение останавливается.

## v0.1 — read-only inventory + dry-run

Цель: система понимает поток почты, но ничего не меняет.

### Почтовые адаптеры
- [ ] Gmail OAuth только с необходимыми read-only правами.
- [ ] Microsoft Graph OAuth только с необходимыми read-only правами.
- [ ] Инвентаризация Gmail labels/filters.
- [ ] Инвентаризация Outlook folders/message rules.
- [ ] Инкрементальная синхронизация Gmail.
- [ ] Инкрементальная синхронизация Outlook.

### Состояние
- [ ] SQLite schema для provider cursors, message metadata, decisions, actions и incidents.
- [ ] Не сохранять полные тела писем по умолчанию.
- [ ] Ротация локального журнала.
- [ ] Безопасная резервная копия SQLite.

### Policy
- [ ] `categories.yaml`.
- [ ] `rules.yaml`.
- [ ] `retention.yaml`.
- [ ] `protected.yaml`.
- [ ] `control-queue.yaml`.
- [ ] Разделение `external` и `managed` server rules.
- [ ] Детерминированный классификатор.

### Исполнение
- [ ] `mailctl inventory`.
- [ ] `mailctl sync --dry-run`.
- [ ] `mailctl policy plan`.
- [ ] `mailctl audit`.
- [ ] `systemd timer` для read-only sync.

### Gate v0.1 → v0.2
- несколько дней/неделя стабильной синхронизации без потери cursor state;
- нет чтения/хранения лишних данных;
- детерминированные правила дают высокую точность на проверенной выборке;
- dry-run отчёт объясняет каждое предлагаемое действие;
- protected/control-классы никогда не попадают в опасные предложения.

## v0.2 — обратимые изменения

Цель: включить только хорошо проверенные операции с ограниченным blast radius.

- [ ] Добавить минимальные write scopes отдельно от read-only этапа.
- [ ] Назначение Gmail labels.
- [ ] Архивирование Gmail.
- [ ] Перемещение Outlook messages.
- [ ] Read-back verification после каждой записи.
- [ ] Ограничение количества изменений за запуск/сутки.
- [ ] `mailctl policy apply`.
- [ ] Компиляция стабильных `managed` правил в Gmail filters.
- [ ] Компиляция стабильных `managed` правил в Outlook message rules.
- [ ] Безопасная замена Gmail filter через create → verify → delete old.
- [ ] Поддержка защищённого Gmail Control Queue для `status`, `audit`, `dry-run report`, `pause/resume`.
- [ ] Никаких массовых изменений старого архива.

### Gate v0.2 → v0.3
- read-back стабильно совпадает с `expected_state`;
- нет неожиданных изменений внешних правил;
- лимиты blast radius протестированы;
- recovery-mode останавливает операции при расхождении;
- управляющий канал не воспринимает произвольное письмо как команду.

## v0.3 — ИИ-советник

Цель: ИИ помогает классифицировать неизвестные случаи, не получает возможности самостоятельно изменять почту.

- [ ] Минимальный sanitised input: headers + короткий очищенный фрагмент + признаки вложений.
- [ ] Строгая JSON Schema ответа.
- [ ] Категория + confidence + retention class + action hint + reason code.
- [ ] Первая дешёвая модель для массовых неизвестных случаев.
- [ ] Эскалация на более сильную модель при низкой уверенности/конфликте.
- [ ] `REVIEW_REQUIRED` как безопасный исход.
- [ ] Тесты prompt injection из тела письма.
- [ ] ИИ не имеет Gmail/Graph write, shell, SSH или произвольного web.
- [ ] Недельный аудит ошибок и новых массовых шаблонов.
- [ ] ИИ предлагает изменения policy как diff/PR, но не применяет их напрямую.

### Gate v0.3 → v0.4
- измерена точность на отложенной проверочной выборке;
- ошибки ИИ не приводят к необратимым действиям;
- отказ API/модели переводит случаи в review, а не ломает основной поток;
- deterministic core полностью работоспособен без ИИ.

## v0.4 — retention + миграция старой почты

### Retention
- [ ] Расчёт возраста и retention class.
- [ ] `protected`, `hold`, `action_required` имеют абсолютный приоритет.
- [ ] Несколько недель retention dry-run.
- [ ] Перемещение просроченных сообщений только в Trash.
- [ ] Permanent delete отсутствует в API/CLI проекта.
- [ ] Отчёт о запланированном удалении до включения write-mode.

### Историческая миграция
- [ ] Сопоставление старых Outlook folders с новыми категориями.
- [ ] Миграция только хорошо определённых массовых классов.
- [ ] Финансы, документы, недвижимость и безопасность — отдельные осторожные проходы.
- [ ] Старые server rules удалять только после подтверждённой замены.
- [ ] Сохранить поиск и доступ к историческим данным.

## После v0.4

Возможные направления только после появления реальной необходимости:

- push/webhook вместо polling;
- отдельная очередь ручного review;
- экспорт ценных вложений в файловое хранилище;
- статистика качества и стоимости ИИ;
- дополнительные почтовые провайдеры;
- ChatGPT Work для крупных разовых аудитов.

Не являются целью по умолчанию: Docker, Kubernetes, Redis, PostgreSQL, постоянно работающий Codex/OpenCode или универсальный autonomous agent на VPS.
