# Подготовка серверного адаптера Gmail

## Разделение сред

`src/mail_organizer/gmail.py` — часть собственного Python-пакета серверного
`mail-organizer`. Это узкий обработчик метаданных, не универсальный ИИ-агент.
Он не импортирует коннекторы ChatGPT, MCP-инструменты, браузерную сессию или Work.
Авторизация Gmail в ChatGPT **не авторизует** этот пакет и не является способом
передачи credentials на сервер. Для Outlook будет нужен отдельный адаптер Graph.

В этом срезе реализованы разбор ответов, подготовка окна history и связь с SQLite.
`GmailReader.read(operation, parameters)` задаёт интерфейс будущего собственного
HTTPS/OAuth-транспорта. Добавлен собственный ограниченный HTTPS reader с обновлением
ранее выданного grant и сверкой ожидаемого аккаунта: [GMAIL_CLIENT.md](GMAIL_CLIENT.md).
Первичное OAuth-согласие, публичная команда подключения ящика, начальная
инвентаризация и служба systemd **ещё не реализованы**. Рабочий допуск к настоящему
ящику не заявляется; пользовательские данные при разработке не читались.

## Метаданные и права

Кандидат первого минимального OAuth scope —
`https://www.googleapis.com/auth/gmail.metadata`. Он позволяет читать метки и
заголовки, не тело сообщения. Запросы проектируются только для `labels.list`,
`history.list`, `messages.get`; для сообщения задан `format=metadata`, заголовки
`From` и `Subject`, ограниченный `fields`. Никаких send/modify/delete, вложений,
raw MIME, body или snippet. Любой будущий HTTP-клиент должен ограничивать также
размер ответа, время запроса и обработку ошибок до передачи данных адаптеру.

Инвентаризация Gmail filters пока не входит в этот scope и срез. Её права будут
проверяться отдельно; недостаток разрешений не должен автоматически расширять
OAuth scope. Существующие server rules не принимаются под управление и не меняются.

Метки Gmail имеют непрозрачные ID. Перед преобразованием сообщений адаптер читает
`labels.list`, связывает ID с именами и только затем проверяет protected scope.
Неизвестная метка останавливает окно; она не считается обычной меткой по умолчанию.
`ChatGPT-Control/...` сохраняет приоритет даже при отсутствии корректного From.

Домен берётся из единственного разобранного From. Это признак классификации,
**не** доказательство подлинности отправителя и не авторизация Control Queue.
Отсутствующий/неоднозначный From или неразбираемая тема дают неизвестный признак
и `REVIEW_REQUIRED`. Тема без Subject считается пустой; MIME-кодировка декодируется.
Содержимое заголовка остаётся данными и никогда не исполняется.

Формат metadata не доказывает отсутствие вложений: `has_attachments=None`,
в SQLite — `NULL`. Правила, которым потребуется этот признак, должны учитывать
неизвестность; добавлять чтение тела ради заполнения boolean запрещено без отдельной
оценки необходимости. Поля темы/домена/меток существуют только в памяти; сохраняются
минимальные метаданные, решения и предложения.

## Окно изменений и состояние

Адаптеру нужны существующий `Checkpoint(revision>0, cursor=<historyId>)` и
scope `gmail-history-all-v1`. Число historyId не считается непрерывным счётчиком;
его не увеличивают самостоятельно. Начальная версия 0 возвращает
`initial_inventory_required`, без обращения к источнику. Отправная точка в тестах
задана искусственно; она **не заменяет** начальную инвентаризацию настоящего ящика.

Во всём окне передаётся один исходный `startHistoryId`. `nextPageToken` используется
только в памяти; это не долговременный cursor. Промежуточный `historyId` не
сохраняется: только после завершения пагинации берётся последний возвращённый
`historyId`, а все уникальные изменённые сообщения перечитываются как metadata.
Дублирующий `history.messages` не создаёт повторных записей.

Лимиты одного окна: 10 страниц, 100 history records суммарно и 100 уникальных
сообщений. Превышение лимита, цикл токенов, неизвестная структура, нарушенный
порядок или несовпадение ID останавливают окно без продвижения cursor.
Лимит — явная граница подготовки, не доказательство готовности больших ящиков.
Нельзя обрезать окно и сохранить последний замеченный historyId.

`sync_history` читает исходное ожидаемое состояние, готовит всё окно и вызывает
единственный `commit_page`. SQLite проверяет expected revision/value и policy;
устаревший писатель не перезапишет изменения другого процесса. Если historyId не
изменился, возвращается `no_changes`, без SQLite-записи и чтения сообщений.
Пустое, но продвинувшееся окно может сохранить новый cursor.

Точный повтор **подготовленной страницы** распознаётся квитанцией SQLite.
Это не обещание идентичности повторного сетевого чтения: метаданные у провайдера
могли измениться. После неопределённого COMMIT нужна диагностика текущей SQLite;
программа не повторяет окно автоматически. Обычная искусственная фикстура связывает
cursor только с alias. Новый собственный [клиент](GMAIL_CLIENT.md) сначала сверяет
getProfile и добавляет account binding; старые непривязанные данные не принимаются
под подтверждённый аккаунт задним числом.

## Ошибки

- History HTTP 404 → `cursor_expired`; нет автоматического сброса или полной загрузки.
- HTTP 401/403 → `access_denied`; нет повторного согласия или расширения scopes.
- HTTP 429/5xx, сбой транспорта → остановка без автоматического повтора.
- Исчезновение сообщения при `messages.get` → `message_disappeared`; окно не фиксируется.
- Событие удаления → `deletion_requires_inventory`. Tombstones и согласование локального
  снимка ещё не реализованы; пропуск удаления с продвижением cursor запрещён.

Собственный транспорт передаёт `ReadFailure(status)` без чувствительного тела ответа.
Адаптер выдаёт только фиксированные коды ошибок. Исключение транспорта с URL,
заголовками или токеном не печатается и не становится журналом. Это контракт
интерфейса, а не изоляция произвольного кода собственного транспорта.

Схема SQLite теперь 4: после nullable признака вложений добавлена привязка аккаунта.
Старые искусственные схемы 2/3 отклоняются без изменения. Автоматической миграции
или удаления старой БД нет.

## Проверки и следующий этап

```bash
PYTHONPATH=src python -m unittest discover -s tests -p test_gmail.py -v
PYTHONPATH=src python -m unittest discover -s tests -v
```

Искусственные ответы находятся в `tests/fixtures/gmail_history.json`. Проверяются
две страницы с пропусками historyId, повторные ID, protected-метка с непрозрачным ID,
неизвестные вложения, остановка при expiry/доступе/удалении/лимитах, отсутствие
сырого содержимого в SQLite и связь с прежними проверками транзакций.

Перед реальным подключением нужны отдельные проверяемые результаты:

1. Первичное OAuth-согласие для собственного приложения, а не коннектора ChatGPT.
   Тип клиента, PKCE и процедура авторизации выбираются для фактического запуска.
2. Приёмка реализованного HTTPS/refresh в фактической среде: доверенные CA,
   внешнее ограничение времени процесса, состояние grant после отказов и отзыва.
3. Проверка expected_email и реального getProfile, уже реализованная привязка
   alias/scope и защищённый каталог credentials вне Git. Секреты не передаются через чат.
4. Начальная инвентаризация с корректным переходом к history; явный план после
   истечения cursor, обработки удаления и превышения текущих лимитов.
5. Отдельно согласованные ящик, минимальные права и ограниченный первый read-only
   запуск. Для установки на VPS остаются требования Stage 0 и открытый блокер подготовки.
