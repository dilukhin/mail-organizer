# Собственный HTTPS-клиент и обновление OAuth для Gmail

## Граница этого среза

Добавлены `gmail_http.py`, `gmail_oauth.py` и `gmail_client.py`. Это собственный
серверный Python-код, без коннекторов ChatGPT Web/Work, браузерных сессий, Gmail SDK
или сторонних runtime-зависимостей. Команды CLI по-прежнему работают только с
искусственными файлами. Новый сетевой код вызывается только явно через Python API;
импорт пакета и существующий `sync --dry-run` сеть не включают.

Реализованы HTTPS-транспорт, один явный refresh уже выданного OAuth grant,
проверка ожидаемого Gmail-аккаунта и постоянная привязка SQLite. Первичная выдача
согласия/PKCE, браузерный callback, регистрация OAuth-приложения, начальная
инвентаризация, удаления и восстановление после expiry ещё не реализованы.
Сквозная проверка использует искусственную отправную history-точку. Это не допуск
к самостоятельному подключению реального ящика или развёртыванию на VPS.

## Закрытый сетевой интерфейс

| Узел | Метод и путь | Назначение |
|---|---|---|
| `oauth2.googleapis.com:443` | POST `/token` | Только `grant_type=refresh_token` |
| `gmail.googleapis.com:443` | GET `/gmail/v1/users/me/profile` | Только `fields=emailAddress` для сверки ящика |
| тот же узел | GET `.../labels`, `.../history`, `.../messages/<ID>` | Только параметры и fields предыдущего адаптера |

Произвольные URL, другой userId, write-методы, `format=full/raw`, дополнительные
поля и тело Gmail-запроса не принимаются. Page token кодируется как значение query,
а не используется как URL. Bearer token передаётся только в заголовке Authorization.
OAuth client secret и refresh token передаются только в теле фиксированного POST.
В URL, обычные журналы и исключения секреты не добавляются.

Используется `http.client.HTTPSConnection`: доверие системному хранилищу CA,
проверка имени узла, минимум TLS 1.2, ALPN HTTP/1.1. Debug вывода HTTP отключён
явно. Перенаправления не выполняются; прокси из переменных окружения не используются.
HTTP-ошибки и redirects не читают тело ответа и не запускают новый запрос.
Нет обхода TLS, пользовательского endpoint, автоматического retry или revoke.

Ответы: JSON UTF-8, без сжатия, максимум 64 КиБ для OAuth и 1 МиБ для Gmail.
Проверяются Content-Type/Length/Encoding и неоднозначные сочетания length/transfer.
Повтор JSON-ключа, NaN/Infinity и вложенность свыше 32 отклоняются. Длина проверяется
и по заголовку, и по прочитанным байтам. Ошибки заменяются фиксированными сообщениями.

Таймаут блокирующей socket-операции — 10 секунд. Бюджет 20 секунд проверяется
между чтениями тела и перед положительным возвратом. Это **не жёсткое прерывание**
DNS и медленно поступающих HTTP-заголовков: стандартная библиотека не предоставляет
здесь общего прерываемого deadline. До автономного развёртывания нужен внешний
предел времени процесса и отдельная проверка фактической среды. При превышении
замеченного бюджета положительного результата нет.

## Собственный OAuth-файл

Текущий файловый загрузчик предназначен для POSIX/Linux. Нужен заранее выданный
grant отдельного OAuth-приложения `mail-organizer`, без зависимости от авторизации
ChatGPT. Файл — обычный, с одним hard link, принадлежит текущему пользователю,
без групповых/общих прав. Его непосредственный каталог должен принадлежать тому же
пользователю и иметь права 0700; symlink для файла или непосредственного каталога
отклоняется. Предки каталога должны быть доверены оператору. Это не изоляция от
того же UID, root или подмены доверенного окружения/CA. Шифрования файла нет.

Закрытый формат версии 1:

```json
{
  "schema_version": 1,
  "client_id": "SYNTHETIC-CLIENT-ID",
  "client_secret": "SYNTHETIC-CLIENT-SECRET",
  "refresh_token": "SYNTHETIC-REFRESH-GRANT",
  "expected_email": "demo@example.invalid",
  "scopes": ["https://www.googleapis.com/auth/gmail.metadata"]
}
```

Пример искусственный, не является действующей конфигурацией. Файл располагается
вне Git, например в отдельном пользовательском каталоге credentials. Не создавать
его из секретов в чате или копированием токенов коннектора ChatGPT. Файл нельзя
использовать как произвольный Google SDK credential document: неизвестные поля,
включая пользовательский token_uri, отклоняются. Access token на диск не пишется.

`refresh_session(path)` берёт неблокирующий `flock`, проверяет файл и выполняет
ровно один POST. Он требует от token endpoint точного `scope=gmail.metadata`,
`token_type=Bearer`, допустимого токена и целого срока 60–86400 секунд. Если сервер
не вернул scope, программа останавливается вместо предположения о правах.
Дополнительные scopes не запрашиваются и не принимаются. Уменьшенный на 30 секунд
срок access token отсчитывается монотонными часами с момента начала refresh.
Сессия не обновляет токен автоматически по 401 или expiry.

DPoP и другие виды grant этим срезом не поддерживаются. Первичная авторизация
остаётся отдельной задачей; до её реализации нельзя объявлять локальное поле
`scopes` доказательством выданного Google согласия.

## Refresh, ротация и неопределённый исход

В приватном каталоге хранится отдельная запись `.mail-organizer-refresh-<hash>.json`.
Она содержит только фазу и SHA-256 исходного credential-файла, без токенов/адресов.
Перед POST фаза `refresh_pending` записывается и подтверждается чтением/fsync.
Повторный запуск с pending, неизвестной записью или несовпадающим digest
останавливается до сети. Автоматического удаления/сброса pending нет.

При новом refresh token создаётся приватный файл-кандидат 0600, записывается,
проверяется чтением и fsync. Кандидат сохраняется и при последующем отказе scope
или expiry: новый секрет не теряется только из-за отказа допуска к access session.
Он не является одобрением расширенных прав и не устанавливается автоматически
при таком отказе.

При полностью проверенном ответе исходный credential-файл повторно сравнивается
с ожидаемыми байтами. Новый файл устанавливается атомарной заменой; выполняются
fsync каталога и read-back. Неожиданно изменённый файл не перезаписывается.
Даже если ротации нет, исходный файл проверяется перед положительным завершением.

После подтверждения критических шагов запись refresh атомарно переходит в
`refresh_completed` с digest итогового credential-файла. Только совпадающий
completed допускает новый **явный** запуск. Запись не удаляется ради очистки.
Если ответ о завершении был потерян, видимый completed и совпадающий digest
являются свидетельством завершённого предыдущего обновления. Pending — такого
свидетельства не даёт. Это протокол одного доверенного владельца, а не защита от
подделки файлов тем же UID и не полный неизменяемый журнал.

При сбое остаются старый/новый основной файл, pending и, возможно, приватный
кандидат/промежуточная запись. Нужна отдельная локальная диагностика; не следует
удалять их, переименовывать grant для обхода блокировки или повторять POST вслепую.
Программа не публикует содержимое этих файлов и не пытается восстановить доступ
новым человеческим согласием. Сохранность при отключении питания или неисправной
файловой системе unit-тестами не доказана.

## Ожидаемый ящик и SQLite

`GmailHttpsReader(session, scope)` сначала выполняет getProfile и сравнивает
emailAddress с заранее заданным expected_email. Регистр нормализуется; точки,
plus-алиасы и разные домены не отождествляются. При несовпадении metadata/history
не читаются. From письма для этой проверки не используется.

Fingerprint привязки включает provider, ожидаемый email, OAuth client ID и
единственный scope. `bind_identity` в SQLite связывает только новый пустой alias;
существующие непривязанные сообщения или cursor не принимаются задним числом.
Смена ящика, OAuth client ID или scope останавливает обработку. Реальный email
в таблицу не записывается, но digest не считается обезличиванием.

`sync_verified_history` проверяет привязку до чтения history, а `commit_page`
повторно сверяет её внутри транзакции. Для привязанного alias нельзя использовать
прежнюю запись без identity digest, даже при повторе квитанции. Синтетические
непривязанные фикстуры продолжают работать отдельно. Текущая схема SQLite — 4;
схемы 2/3 отклоняются без миграции, перезаписи или удаления. Нужен новый файл для
новой искусственной демонстрации; старые файлы сохраняются.

Fingerprint и объект AccessSession не дают защиты от произвольного Python-кода
в том же процессе. Доверие исходит из фиксированного проверенного HTTPS-клиента,
защищённого локального grant и заранее известного ожидаемого ящика. Это не новая
система привилегий OpenCode и не решение блокера подготовки VPS.

## Проверки и оставшиеся условия

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
```

Тестам нужен Python 3.11+, OpenSSL CLI и доступный loopback. Настоящие TLS-сеансы
идут только к 127.0.0.1 с одноразовым искусственным ключом/сертификатом. Проверяются
правильный TLS, отказ на недоверенный сертификат/неверное имя узла и отсутствие
перехода по redirect. Учётные записи Google и внешний DNS не используются.

Другие тесты заменяют только HTTPSConnection либо фиксированный обмен. Сквозная
искусственная цепочка проходит refresh → profile → history → labels/metadata →
SQLite. Проверяются отказы/лимиты, ротация, pending/completed, drift, безопасные
исключения, истечение сессии и невозможность связать старый cursor с новым ящиком.
Эти тесты не являются проверкой настоящего согласия пользователя или Google API.

До первого настоящего чтения остаются: проверенная первичная OAuth-авторизация,
начальная инвентаризация с корректным переходом к history, согласование удаления
и истечения cursor, ограниченный scope первого запуска и отдельное разрешение
на выбранный ящик. Установка на VPS требует завершения Stage 0.
