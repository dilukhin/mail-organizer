# Автономное состояние и искусственные страницы

Этот срез продолжает v0.1: файл SQLite сохраняет минимальные метаданные,
последние решения, предложения dry-run и курсор между запусками. Сетевых
адаптеров, OAuth и операций с почтой в нём нет. Использовать только искусственные
данные. Подготовка VPS и переход к реальной почте остаются отдельными этапами.

## Запуск

Старый `sync --dry-run --fixture ...` по-прежнему создаёт SQLite только в памяти.
Новый режим записывает **указанный локальный файл SQLite**, хотя не меняет почту.
Создание файла выполняется отдельной явной командой, без перезаписи существующего:

```bash
# Каталог должен существовать и принадлежать только оператору; пример — временный.
demo_dir=$(mktemp -d)
PYTHONPATH=src python -m mail_organizer state-init --database "$demo_dir/demo.sqlite3"
PYTHONPATH=src python -m mail_organizer sync-pages --dry-run --fixture tests/fixtures/offline_pages.json --policy-dir policy --database "$demo_dir/demo.sqlite3"
# Повтор распознаёт обе страницы и ничего не дублирует.
PYTHONPATH=src python -m mail_organizer sync-pages --dry-run --fixture tests/fixtures/offline_pages.json --policy-dir policy --database "$demo_dir/demo.sqlite3"
```

Результат первого запуска: две сохранённые страницы. Второго: две уже сохранённые.
Во второй странице искусственное сообщение получает защищённую метку: его прежнее
предложение убирается, решение становится `PROTECTED`. Никакой метки у провайдера
это не создаёт. CLI выводит только числа страниц и общие статусы; курсоры,
идентификаторы, темы и отправители в отчёт не попадают. Общая ошибка CLI намеренно
не печатает исходное исключение, путь или содержимое входа.

## Контракт страницы

Фикстура имеет закрытый набор полей, `schema_version=1`, provider (`gmail` либо
`outlook`), локальный `account_alias`, `scope_key` и от 1 до 100 страниц.
Одна страница — не более 100 сообщений, весь файл — не более 2 МиБ.
Все сообщения страницы должны относиться к указанному провайдеру и ящику.
Поля сообщения проверяет тот же разбор, что и в первом офлайн-срезе;
неизвестные поля, тело и HTML отклоняются.

Каждая страница задаёт:

- `batch_id`: стабильный локальный идентификатор страницы;
- `expected_revision` и `expected_cursor`: точное ожидаемое состояние;
- `next_cursor`: следующий непрозрачный курсор, отличный от предыдущего;
- `messages`: искусственные признаки сообщений.

Начальное состояние — версия 0 и курсор `null`. После каждого сохранения версия
увеличивается на 1. Сравниваются и значение, и версия: возврат значения курсора
к ранее встречавшемуся не разрешает устаревшему процессу записать страницу.
Пустая страница допустима, если продвигает курсор.

Пока поддерживается **один неизменный scope на один provider/account_alias**.
Это ограничение не моделирует отдельные папки Graph. Смена scope или policy
останавливает новые страницы и требует отдельного плана пересчёта; автоматического
сброса, создания новой области или переоценки старых сообщений нет.
Правила приводятся к проверенному упорядоченному представлению; их SHA-256
фиксируется вместе с курсором. Добавление/удаление/изменение правила меняет привязку.

## Атомарность и повтор

`BEGIN IMMEDIATE` сериализует запись. Проверка ожидаемого состояния, метаданные,
решения, текущие предложения, курсор и квитанция страницы сохраняются одной
транзакцией. `COMMIT` завершается до положительного ответа, затем курсор
проверяется чтением. Настроены `foreign_keys=ON` и `synchronous=FULL`.

В `sync_batches` уникальны идентификатор страницы и номер версии внутри области.
SHA-256 связывает полное проверенное содержимое страницы, её ожидаемое состояние
и policy. Точный повтор получает `already_committed`, даже если следующие страницы
уже обработаны. Тот же `batch_id` с другим содержимым отклоняется.
Другой `batch_id` с устаревшим ожидаемым состоянием тоже отклоняется.

`message_metadata`, `decisions` и `actions` представляют **последний локальный
снимок**, а не историю исполнения. При повторном наблюдении сообщения его
предыдущее предложение заменяется или убирается. В `actions` возможны только
`dry_run`/`proposed_only`. Квитанции страниц сохраняются; журнал реальных
почтовых действий и полноценный аудит этим срезом не реализованы.

При ошибке записи/COMMIT соединение блокируется, положительного ответа нет,
автоматический повтор в текущем запуске отсутствует. Отказ SQLite из-за другого
писателя также останавливает обработку без ожидания и повторов. Возможен частичный
успех **между страницами**: ранее завершённые страницы остаются сохранёнными.

После диагностики и повторного открытия БД точный повтор фикстуры распознаёт
сохранённые страницы. Если COMMIT был выполнен, а ответ потерян, квитанция уже есть;
если не выполнен — локальная транзакция откатилась. Такая повторяемость допустима
здесь потому, что внешних почтовых действий вообще нет. Она не доказывает
однократность будущих Gmail/Graph write-операций или привилегированного доступа.

## Хранение и ограничения

Файл создаётся эксклюзивно с правами 0600. На POSIX открытие требует владельца —
текущего пользователя и отсутствия групповых/общих прав; символические ссылки
отклоняются. Это **не** защита от другого процесса с тем же UID, подмены каталога
или администратора. Нужен доверенный отдельный каталог; Windows ACL не проверяются.
SQLite не шифруется. Курсоры и идентификаторы следует считать чувствительными.
Отпечатки нужны для повтора, а не для обезличивания данных.

Отсутствующая БД не создаётся командой синхронизации. Неизвестная/повреждённая схема
и старая версия отклоняются без пересоздания, очистки или миграции. Текущая схема
имеет версию 3: признак вложений допускает `NULL` («неизвестно»). Версия 1
существовала только в памяти; искусственные файлы версии 2 не мигрируются
автоматически и не перезаписываются. Для новой демонстрации нужен новый путь БД;
старый файл сохраняется. Неудачное создание может
оставить файл для диагностики, автоматически удалять его программа не будет.

Темы, домены отправителя, метки, тела и вложения не сохраняются. В БД остаются
идентификаторы, время получения, признак вложений, решения, предложения, курсоры,
версии и SHA-256. Файлы SQLite и служебные файлы журнала должны оставаться вне Git.

Тесты на временной SQLite проверяют повтор после открытия, изоляцию ящиков,
устаревшего писателя, сбой в середине страницы, ошибки COMMIT до/после фиксации
и аварийное завершение дочернего Python-процесса. Они не имитируют отключение
питания, неисправности файловой системы или многодневную работу провайдера.

Разбор Gmail history и остановка на истёкшем курсоре добавлены отдельным
[серверным адаптером](GMAIL_ADAPTER.md), проверенным на искусственных ответах.
Для прежнего `sync-pages` курсоры по-прежнему являются искусственными строками.
`sender_domain` и `subject` допускают `null` для неполных метаданных: обычная
классификация выдаёт `REVIEW_REQUIRED`, а protected scope сохраняет приоритет.
Пустая тема допустима. `has_attachments=null` не означает отсутствие вложений.

Пока не реализованы: реальный Gmail/Graph transport и OAuth, начальная и управляемая
повторная инвентаризация, удаления/перемещения сообщений, проверенные идентичности
учётных записей OAuth, резервное копирование, миграции, ротация/квоты журнала,
полноценные incidents и systemd. Офлайн-тесты не являются испытанием реального API.
