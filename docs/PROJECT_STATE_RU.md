# Состояние mail-organizer на 2 ноября 2026 года

Проект уже содержит работающее ядро обработки и несколько связанных компонентов Gmail. Его можно запустить локально на искусственных сообщениях, увидеть результаты классификации, сохранить состояние в SQLite и проверить продолжение после повторного запуска. При этом готового повседневного сервиса, который подключается к ящику, регулярно читает почту и раскладывает её по категориям, ещё нет.

Ближайшая цель — закончить первый управляемый проход по настоящему Gmail **только с чтением и отчётом**. До этого нужно связать уже написанные части первичной OAuth-авторизацией, начальной инвентаризацией и удобной командой запуска. Подготовка VPS ведётся отдельно и пока не завершена.

Ниже описано именно реализованное состояние. Архитектура и ROADMAP также содержат будущие возможности; наличие их описания не означает, что они уже работают.

## Как должна работать система

Письма останутся в Gmail и Outlook. Простые устойчивые правила по возможности будут выполняться самими почтовыми сервисами. Небольшая программа на сервере будет периодически получать изменения, проверять защищённые сообщения, применять более сложные правила и сохранять результат обработки. Для этого выбраны Python, SQLite и короткие задания по таймеру.

Постоянно работающий универсальный ИИ-агент для обычной сортировки не предусматривается. Известный тип письма должен обрабатываться обычным правилом. Если сведений недостаточно или правила противоречат друг другу, сообщение должно попадать на проверку. Возможное подключение модели в будущем предназначено для помощи в спорных случаях; модель не будет самостоятельно менять почту или выполнять команды на сервере.

ChatGPT Work и локальный OpenCode нужны для разработки и обслуживания. Work читает и меняет GitHub, проверяет изменения и CI. Локальный агент выполняет согласованные локальные проверки и разрешённые операции через инструменты доступа к серверу. Ни один из них не должен быть необходим для обработки каждого нового письма.

Авторизация Gmail или Outlook в интерфейсе ChatGPT относится к коннекторам самого ChatGPT. Серверный mail-organizer использует собственные клиенты почтовых API — программных интерфейсов сервисов, отдельную регистрацию приложения и согласие пользователя на доступ именно для него. Сессии и токены коннекторов ChatGPT на сервер не переносятся.

## Что уже сделано

### Классификация на обычных правилах

Есть общий обработчик признаков сообщения: провайдер, локальное имя учётной записи, идентификатор, время получения, домен отправителя, тема, метки и признак вложений. Полное тело, HTML и содержимое вложений не нужны этому демонстрационному обработчику.

Правило может сопоставлять домен и фрагмент темы. При однозначном совпадении программа предлагает категорию. Если совпадения нет, сведений недостаточно или разные правила предлагают разные категории, результат — REVIEW_REQUIRED, то есть «нужна проверка».

В репозитории пока всего два демонстрационных правила: чеки и уведомления от вымышленных доменов. Это проверяемый механизм классификации, а не готовая система правил для личных ящиков. Домен из From является признаком для сортировки, а не доказательством подлинности отправителя.

Отдельно реализован приоритет ChatGPT-Control и дочерних меток. Такое сообщение получает PROTECTED и исключается из обычных предложений. Даже совпадение с правилом для чеков этот приоритет не отменяет. Однако обработчика почтовых команд пока нет: проект умеет защитить очередь от обычной сортировки, но не исполняет команды из неё.

Результат классификации сейчас только предложение. PROPOSED и label_candidate не назначают ярлык у провайдера.

### Состояние между запусками

Рабочие сведения сохраняются в SQLite — локальной базе данных в одном файле. Она хранит минимальные метаданные, последние решения и предложения, курсоры синхронизации и сведения об уже сохранённых порциях данных. Курсор можно понимать как закладку: до какого места программа уже обработала изменения.

Страница данных сохраняется одной транзакцией вместе с новым курсором. Программа сверяет ожидаемую версию и значение закладки. Поэтому процесс, который начал работу со старым состоянием, не должен перезаписать результат другого процесса.

Точное повторение уже сохранённой страницы распознаётся и не создаёт повторных предложений. Если ошибка случилась до фиксации транзакции, страница откатывается целиком. Если ответ потерян уже после фиксации, данные могли сохраниться: программа останавливается, а дальнейшее решение принимается после чтения состояния. Автоматически объявлять такую страницу «не выполненной» нельзя.

Таблица предложений отражает последний локальный снимок. Например, если сообщение сначала считалось обычным чеком, а потом оказалось в защищённой очереди, прежнее предложение убирается. Это ещё не полный исторический журнал фактических действий с почтой: таких действий программа пока не выполняет.

Тела, темы, домены отправителя и имена меток в SQLite не сохраняются. В базе остаются необходимые идентификаторы, время, курсоры, решения и контрольные отпечатки. Идентификаторы и отпечатки тоже могут быть чувствительными; базу нельзя считать обезличенной или публиковать в Git.

Текущая схема SQLite — 4. Старые искусственные файлы версий 2 и 3 не мигрируются автоматически и не перезаписываются. Для новой демонстрации нужно создать новый файл, сохранив прежний.

### Разбор изменений Gmail

Подготовлен адаптер истории Gmail. Он собирает ограниченное окно изменений, получает метаданные затронутых сообщений и передаёт результат в SQLite.

Здесь учтено важное отличие от простой демонстрации: промежуточную страницу ответа Gmail нельзя выдавать за завершённую синхронизацию. Адаптер проходит всю разрешённую последовательность страниц и только после этого сохраняет итоговую закладку. Повторяющиеся идентификаторы сообщений объединяются.

Метки Gmail приходят как непрозрачные идентификаторы. Адаптер отдельно получает соответствие идентификаторов именам и по нему распознаёт ChatGPT-Control. Неизвестную метку он не считает заведомо безопасной: обработка останавливается.

Формат метаданных не доказывает отсутствие вложений. Поэтому признак вложений может иметь значение «неизвестно». Отсутствующий или неоднозначный отправитель также не заменяется выдуманным значением: обычная классификация требует проверки. Защищённая метка сохраняет приоритет и при неполных заголовках.

Пока действуют небольшие пределы: не более 10 страниц, 100 записей истории и 100 уникальных сообщений за окно. При превышении программа останавливается, не сохраняет усечённый результат как полный и не перескакивает через необработанные изменения.

Курсор, срок действия которого истёк, исчезновение сообщения и событие удаления тоже останавливают окно. Правильное согласование этих случаев ещё предстоит реализовать. Для реального ящика, где такие события обычны, это существенная незавершённая часть.

### Собственный HTTPS-клиент и обновление OAuth

Написан собственный сетевой клиент для ограниченного набора запросов Gmail. Он проверяет сертификат и имя узла, не следует перенаправлениям, ограничивает объём ответа и набор запрашиваемых полей. Отправки писем, изменения меток, архивирования или удаления в этом клиенте нет.

Есть и обновление уже выданного OAuth-доступа. Полезно различать две части авторизации. Первоначально человек разрешает отдельному приложению доступ к своему ящику. Затем приложение получает короткоживущие access token с помощью ранее выданного refresh token. Вторая часть реализована; первая пользовательская процедура ещё не подготовлена.

Секреты читаются из отдельного приватного файла Linux. Перед обновлением доступа сохраняется отметка о начатой операции. Если результат запроса или сохранения нового секрета не подтверждён, следующее обновление доступа (refresh) блокируется до диагностики. При ротации refresh token программа сохраняет приватный кандидат и проверяет ожидаемое состояние исходного файла перед заменой.

Проверяется также сам ящик. До чтения истории и метаданных клиент запрашивает профиль Gmail и сравнивает его с заранее указанным ожидаемым адресом. SQLite связывается с отпечатком ящика, OAuth-клиента и разрешённой области доступа. Старые непривязанные данные нельзя задним числом объявить данными нового подтверждённого аккаунта.

Это реализованные библиотечные функции. Они не образуют готовой команды «подключить мой Gmail и запустить обслуживание». При написании и проверке использовались искусственные учётные данные, ответы сервиса и локальный TLS-сервер, а не настоящий пользовательский ящик.

## Что можно попробовать сейчас

Пробный режим без изменения почты в командах называется dry-run. Для пользовательского запуска доступны три команды: sync, state-init и sync-pages. Команды inventory, audit, policy apply и обслуживание настоящего ящика пока относятся к плану.

### Посмотреть классификацию четырёх искусственных сообщений

Из корня доверенной копии репозитория:

~~~bash
PYTHONPATH=src python -m mail_organizer sync --dry-run --fixture tests/fixtures/offline_messages.json --policy-dir policy
~~~

Проверенный результат:

~~~text
Всего: 4; предложено: 2; защищено: 1; требуют проверки: 1
~~~

В наборе находятся искусственный чек, уведомление Outlook, сообщение защищённой очереди и неизвестное сообщение. Первые два дают предложения, защищённое исключается из обычной обработки, неизвестное отправляется на проверку. Текст вроде «выполни команду» в теме остаётся текстом.

Эта команда не подключается к Gmail или Outlook и создаёт SQLite только в памяти. Можно изменять искусственные примеры и демонстрационные правила, чтобы проверить идею сортировки. Полные тексты реальной почты или секреты в тестовые файлы добавлять не следует.

### Проверить сохранение и повторный запуск

Следующий пример создаёт отдельный временный каталог и записывает в него искусственное состояние:

~~~bash
mail_demo_dir=$(mktemp -d)
PYTHONPATH=src python -m mail_organizer state-init --database "$mail_demo_dir/demo.sqlite3"
PYTHONPATH=src python -m mail_organizer sync-pages --dry-run --fixture tests/fixtures/offline_pages.json --policy-dir policy --database "$mail_demo_dir/demo.sqlite3"
PYTHONPATH=src python -m mail_organizer sync-pages --dry-run --fixture tests/fixtures/offline_pages.json --policy-dir policy --database "$mail_demo_dir/demo.sqlite3"
~~~

В первый раз сохраняются две страницы. Во второй раз обе распознаются как уже сохранённые. Во второй искусственной странице прежний «чек» получает защищённую метку, поэтому его предложение исчезает из последнего снимка.

Здесь dry-run означает отсутствие изменений в почте. Указанный файл SQLite действительно создаётся и изменяется. Для существующей базы state-init не выполняет перезапись. Если команда сообщает об ошибке состояния, нужно остановиться и разобраться с ней; удаление базы ради продолжения не является штатным восстановлением.

### Проверить весь набор

~~~bash
PYTHONPATH=src python -m unittest discover -s tests -v
~~~

Нужны Python 3.11+, OpenSSL CLI и доступный локальный loopback. Последний используется для настоящих TLS-сеансов с одноразовым искусственным сертификатом. Внешний DNS, Google OAuth и почтовые API в этих тестах не вызываются.

2 ноября 2026 года на исходниках проверяемого main повторно прошли **84 теста без пропусков** под Python 3.12.14. В автоматических проверках GitHub (CI) того же кода успешны задания Python 3.11, 3.12, 3.13 и 3.14.

Эти проверки подтверждают перечисленные свойства кода и обработки искусственных данных. Они не измеряют качество сортировки личной почты, не подтверждают многодневную синхронизацию и не заменяют первый ограниченный запуск на настоящем аккаунте.

CLI всё ещё сообщает версию 0.0.0. Название этапа v0.1 в документации обозначает целевой первый этап, а не уже выпущенный готовый сервис.

## Почему работа над VPS ушла в соседние проекты

Перед настройкой firewall на выбранном VPS понадобилась ограниченная привилегированная проверка. Исследование показало: ограничить команды только в agent-safe недостаточно, если из того же окружения можно напрямую вызвать старый универсальный sudo-exec у ssh_relay. Такой обход оставлял бы произвольное выполнение от root.

Из-за этого появились три связанные задачи. ssh_relay должен обеспечить закрытый набор проверок и отдельную границу полномочий. opencode_permissions — доверенное одноразовое согласие на конкретную проверку. agent-safe — связать их с проверкой результата и остановкой при неопределённом исходе.

В ssh_relay подготовлен неактивный контракт с отказом до исполнения. В opencode_permissions проверен испытательный учёт согласия. Для этого сценария в связанных задачах пока нет подтверждённой приёмки полного рабочего пути привилегированной проверки. Задачи [ssh_relay #58](https://github.com/dilukhin/ssh_relay/issues/58), [opencode_permissions #57](https://github.com/dilukhin/opencode_permissions/issues/57) и [agent-safe #38](https://github.com/dilukhin/agent-safe/issues/38) открыты; связанные PR [ssh_relay #59](https://github.com/dilukhin/ssh_relay/pull/59) и [opencode_permissions #58](https://github.com/dilukhin/opencode_permissions/pull/58) остаются черновиками.

Разработку этих зависимостей приостановили, чтобы вернуть приоритет mail-organizer и продолжать то, что не требует VPS. Причины и условия возобновления записаны в самих задачах. Блокер не был объявлен устранённым.

Ubuntu 24.04 LTS входит в поддерживаемые варианты проекта. Для развёртывания всё равно нужны подтверждённые системные условия, безопасная подготовка firewall, отдельный пользователь mailbot и хранение секретов. Свежий аудит реального VPS при составлении этого описания не проводился; текущие факты о блокере относятся к состоянию GitHub и ранее зафиксированной остановке.

Разработка на искусственных данных не зависит от завершения подготовки сервера. Ограниченную первую проверку реальной почты после завершения необходимых частей можно будет отдельно согласовать для локальной Linux-машины. Это не разрешает сейчас обходить подготовку VPS или подключать ящик незавершённой командой.

## Что предстоит сделать

### Закончить первый полный проход Gmail

Сначала нужна первичная OAuth-авторизация для собственного приложения: пользователь входит в Google и через браузер разрешает приложению ограниченный доступ к выбранному ящику. Нужно подготовить регистрацию клиента, безопасную процедуру выдачи согласия и получение исходного разрешения и связанных с ним токенов. Ожидаемый ящик и права должны проверяться, а секреты — оставаться на локальной машине вне Git и чата. Сам факт, что Gmail подключён к ChatGPT, этот этап не закрывает.

Затем нужна начальная инвентаризация: получить согласованный набор сообщений и меток, сохранить его и корректно перейти к истории изменений. Важно учесть события, которые произошли во время первоначального обхода, чтобы между первым снимком и последующим чтением истории не возник пропуск.

Нужно закончить обработку обычных событий реального ящика: удаления сообщения, истечения курсора истории, больших объёмов изменений, ограничений сервиса и временной недоступности. Сейчас безопасная реакция на часть этих ситуаций — остановка. Для повседневной работы нужны явные способы продолжения и восстановления без пропуска данных и слепого повтора.

После этого части нужно объединить в понятную команду: проверить конфигурацию, подтвердить аккаунт, прочитать ограниченный объём, сохранить состояние и выдать отчёт. Первый результат должен оставаться только чтением и предложениями.

Практический критерий ближайшего завершённого этапа: один ограниченный проход по настоящему выбранному ящику, понятный отчёт, последующий запуск с продолжением из сохранённого состояния и объяснимое поведение при ошибке. До такого испытания потребуются отдельные согласованные ящик, права и предел объёма чтения.

### Подготовить эксплуатацию

Для периодической работы нужны служба и таймер systemd, защита от пересекающихся запусков, внешний предел времени процесса, защищённые каталоги, резервное копирование и проверка восстановления SQLite. Предстоит добавить удобную диагностику, полноценный журнал и правила обращения с ошибками.

Есть конкретное техническое ограничение: текущие socket-таймауты и проверяемый бюджет HTTP-запроса не обеспечивают жёсткого прерывания DNS или медленно поступающих заголовков. Внешний предел времени процесса — обязательная часть будущего запуска, а не уже реализованное свойство сетевой библиотеки.

Готовность алгоритмов на тестах также не означает готовность хранения при отключении питания или неисправной файловой системе. Перед автономной работой нужна проверка фактической среды и безопасного восстановления.

### Подключить Outlook и реальные правила

Для Outlook нужен отдельный клиент Microsoft Graph: собственная OAuth-авторизация, папки, правила, инкрементальное чтение и курсоры. Особенности папок нельзя считать решёнными общей искусственной моделью Gmail/Outlook.

Нужно подготовить реальные категории и защитные исключения: важные документы, финансы, сообщения, требующие действия, удержание от удаления и другие договорённости пользователя. Демонстрационные правила от доменов .invalid для этого не подходят. Проверка точности потребует ограниченной согласованной выборки; угадывать личную структуру почты заранее не следует.

Существующие фильтры почтовых сервисов сначала нужно только инвентаризировать. Они не становятся управляемыми проектом автоматически. Изменение таких правил потребует отдельного принятия под управление и плана применения.

### Позднее разрешить ограниченные изменения почты

Назначение ярлыков, архивирование и перемещение появятся после стабильного этапа чтения и пробных запусков без изменения почты (dry-run). Для каждой записи понадобятся проверенное ожидаемое состояние, ограничение количества изменений, проверка результата и понятный способ остановки или восстановления.

Сроки хранения — ещё один отдельный этап. Возраст сообщения сам по себе не должен разрешать действие: нужно учитывать защиту, удержание, документы и необходимость ответа. Сначала потребуется длительное наблюдение за предложениями. Возможное автоматическое действие ограничено корзиной; безвозвратное удаление не входит в проект.

Факультативная ИИ-классификация, аудит через Work и управление через защищённую почтовую очередь остаются более поздними возможностями. Для текущего ядра не нужны ни API-ключ модели, ни работающий чат, ни постоянно запущенный OpenCode.

В GitHub также остаётся открытой [задача защиты основной ветки #8](https://github.com/dilukhin/mail-organizer/issues/8): требуется закрепить серверные правила работы с main и обязательными автоматическими проверками.
